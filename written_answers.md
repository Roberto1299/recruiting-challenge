## Q1 — Validating production output correctness
An ICD-10 model deployed in production began altering the names of medical conditions—an issue we only noticed because it was reported as a system failure. At the time, I lacked the authorization to formally log the incident. I quickly implemented a temporary change to the system prompt while seeking a permanent fix. I eventually discovered `Response_schema`, which allows for precise control over model outputs; this enabled me to design the output with specific constraints and required fields, offering a level of clarity and specificity far superior to the ambiguity of a simple prompt. The model has functioned correctly since then, though I would approach it differently now: I would implement agents to validate output data and use a workflow graph to determine whether to re-run the function until a validator agent—governed by clearly defined business rules—gave the "green light" to the output.

## Q2 — Forced structural change at scale
We deployed a medical treatment decision-support model using a simple RAG (Retrieval-Augmented Generation) setup. It performed well during tests involving up to ten doctors simultaneously. Following successful pilot testing, we moved to a full production deployment; while it initially behaved well, the RAG system struggled after a few weeks to handle the frequency of requests. It eventually returned a "429" error, indicating that we had exhausted our request quota and had to wait for service to be restored. The metrics that triggered this move were response times and request failures. I proposed to the CEO that we upgrade the RAG system to a more powerful tier—a difficult decision, as it tripled our costs. However, it was a calculated move; while the clock was ticking, I was exploring ways to optimize RAG usage. I combined my knowledge of classical models to create a custom vector-based RAG using the organization's own data. This not only improved speed but also increased accuracy, reducing the average response time from 20 seconds to 6 seconds and striking a balance between Google's RAG and our own cloud-hosted solution.

## P3: A time you rejected an AI result (or accepted an incorrect one and changed your process)
This happened with an AI code-completion feature while using Claude. I took a leap of faith and modified parameters in a class that determined how the agent reacted—specifically, whether it was interacting with an adult or a child—since the entire logic hinged on this distinction. I didn't fully catch the issue because I had to push the change quickly due to urgent implementation instructions; the model we were using had been deprecated, requiring a rapid switch. In the process of distinguishing between "adult" and "child," the name of a parameter received by the method for children was altered. It worked correctly for a week until a case involving a child triggered that specific function, resulting in response errors—nothing that compromised the entire system, but it did affect that specific interaction. Nowadays, I am extremely cautious with corrections; I validate and run functional tests before deploying to development and production environments.
